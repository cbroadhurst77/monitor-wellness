1. Executive Summary

  • Strong safety-first foundation. The engineering already treats this as a photosensitivity-aware, migraine-aware tool: Migraine Mode activates in a single instant step (never a flash/strobe) and always fades out smoothly over 20 seconds; sound feedback is off by default because migraine sufferers often also have sound sensitivity; every comfort feature (history tracking, ambient-light matching, break reminders, ratings) is opt-in, not default-on. This is a genuinely careful base to build the rest of the review on.
  • Top risk — jargon leaking into calm-facing copy. Settings, onboarding, and error text repeatedly surface developer-facing language: "gamma ramp," "Confirmed directly on this hardware," and even direct references to internal files (EVALUATION.md, TECHNICAL_UX_REVIEW.md, IMPLEMENTATION.md) appear in strings the end user actually sees. This conflicts directly with the "patient guidance," first-grade-friendly tone this audience needs.
  • Top risk — no glanceable status. Whether the app is in Day/Night/Deep Night/Migraine/Paused state is only ever visible by hovering the tray icon (tooltip text) or catching a transient 4–15 second balloon notification. Someone mid-migraine, possibly with compromised vision, has no persistent on-screen confirmation of what state they're in.
  • Top risk — dense, small print throughout Settings. The Settings window is a single ~760px scrolling page with 9 stacked sections and pervasive FontSize="10" gray helper text carrying safety-relevant information (gamma-ramp safety warnings, privacy notes, evidence summaries). Small, low-contrast text is a poor fit for a tool explicitly aimed at light/eye-strain-sensitive users.
  • Real (not cosmetic) motion-safety gap. Every scripted transition in the app (schedule changes, migraine fade) is smooth and rate-controlled — except the Settings window's live slider preview, which writes directly to the real screen on every tick with no throttling. A fast drag across a wide Kelvin/brightness range could produce rapid, unthrottled visual change on-screen, which undercuts the app's otherwise-excellent flicker-safety discipline.
  • First-run can be noisy. Depending on hardware/software found at startup, up to three separate balloon notifications (HDR display detected, f.lux conflict, auto-start drift) can appear stacked with the onboarding window on a single first launch — a rocky first impression for a "calm" product.
  • Opportunity — most fixes are copy/UI, not re-architecture. The underlying state machine, safety clamps, and event model are sound and already wired correctly end-to-end (confirmed by reading AppSettings.cs, MigraineModeController.cs, OverlayController.cs, App.xaml.cs). Nearly every P0/P1 item below is a copy rewrite, a style change, or a small amount of new state-surfacing UI — not new backend capability.
  • Opportunity — the evidence story is already good, just buried. The green-tint rationale (Noseda & Burstein, Brain, 2016) and the honest "this is a comfort tool, not a medical device" framing already exist in the app. They're currently hidden inside small, collapsed "Why these colors?" expanders in 10pt gray text — promoting and simplifying this content would turn an already-honest feature into a genuinely reassuring one.

2. UI Audit Checklist

2.1 Navigation & Information Architecture

Screens/sections identified: tray icon + context menu (~14 items, the only "home" screen), Onboarding window (first run only, reachable again via "Help / About..."), Settings window (single scrolling window: Location, Profiles, Day/Night Schedule, Deep Night, Migraine Mode, Monitors, Break Reminders, History), Migraine Rating popup (post-use, opt-in), Profile Name dialog, and the invisible per-monitor Overlay window (not user-facing chrome, but the surface all tint/dim effects render on).

Found issues

  • There is no in-app main window or dashboard at all — every interaction after first-run onboarding routes through a single tray icon and its right-click menu.
  • Settings is one continuous scroll of 9 stacked sections with no jump links, tabs, or grouping — migraine-relevant controls and long-term history controls sit in the same undifferentiated scroll.
  • "Help / About..." reopens the exact first-run onboarding content. That content is written in a "welcome" voice (explaining what the app is), not a "how do I fix X" reference voice — someone reopening it later for help gets the wrong kind of text.
  • Diagnostic-only items (Auto-start Diagnostics, Open Logs Folder) sit at the same menu level as the two everyday actions (Settings, Migraine Mode), lengthening the list a first-time user has to scan.

Recommendations

  • Add a lightweight status surface beyond the tray tooltip — e.g. a small popover on tray left-click-and-hold, or a "Status" line pinned to the top of the Settings window — that states current mode in plain words ("Currently: Day mode" / "Currently: Migraine relief ON, auto-off 3:45 PM").
  • Restructure Settings into grouped sections with a simple left-hand list or tab strip: Schedule, Migraine Mode, Monitors, History & Privacy. UI-only — all underlying settings/fields are unchanged.
  • Split "Help / About" into two distinct entries: "About" (what this is, safety disclaimer) and a short "Help" panel (troubleshooting the known conflict cases the app already detects).
  • Nest diagnostic-only items under a single "Diagnostics" submenu, shortening the everyday menu to roughly 8 visible items.

2.2 Controls & States

Found issues

  • Migraine Mode state is communicated only via tray icon swap (migraine_on.ico/migraine_off.ico), tooltip text (hover-only), and a single 4-second balloon on toggle. There is no persistent on-screen confirmation of an armed auto-revert time unless the tray icon is hovered.
  • The Pause Schedule submenu (30 min / 1 hour / 2 hours / Until tomorrow) leaves the tray tooltip as the only place remaining pause time is visible; the only other signal is the "Resume Schedule" item becoming enabled, which is easy to miss.
  • Every Day/Night/Migraine slider in Settings previews live, directly on the real screen, on every value-changed tick, with no debounce. Dragging quickly across the full Kelvin or brightness range produces rapid, un-throttled real-screen changes.
  • Numeric text-box + slider pairs (a good pattern, added specifically to restore exact-value entry after an earlier "slider-only" regression, per the code's own history) are implemented consistently and commit on Enter or focus-loss — this is a genuine strength worth preserving as new controls are added.

Recommendations

  • Surface Migraine Mode's auto-revert time (if armed) somewhere more persistent than a tooltip — e.g. in the proposed status popover above. Requires minor new UI; no new backend state (AutoRevertAtUtc already exists on MigraineModeController).
  • Give Pause Schedule a small confirmation balloon at the moment it's chosen (mirroring the pattern already used for Migraine Mode toggles), not just a tooltip-text change. UI-only.
  • Add a simple time-based throttle (e.g. apply live preview at most ~10 times/second) around the slider preview calls in SettingsWindow.xaml.cs (DaySlider_ValueChanged, NightSlider_ValueChanged, MigrainePreview_Changed). Small code change, no new feature surface.

2.3 Onboarding & Guidance

Found issues

  • Onboarding is four dense paragraphs in one modal, mixing feature explanation, a hotkey reference, a medical disclaimer, and a location call-to-action in a single wall of text.
  • References a competitor product ("similar to f.lux") and "published research" without simplifying, on the very first screen a new user sees.
  • "Got it, maybe later" doesn't say what is being deferred (the location defaults to London) — it reads as a generic dismissal rather than "you still need to do this one thing."

Recommendations

  • Break onboarding into short, single-idea steps: what it does → Migraine Mode & the hotkey → the safety note → the location prompt. One or two short sentences per step.
  • Rename the two buttons to state the actual choice: "Set my location now" / "Skip for now (uses London times)".
  • Keep the medical disclaimer's content and prominence, but give it a proper visual "note" treatment (background + border, not italics/gray alone) so it reads as important rather than as a footnote.

2.4 Accessibility

Found issues

  • Automation labelling is genuinely good in several places — AutomationProperties.Name is set on sliders, checkboxes, per-monitor rows, and rating buttons, and AutomationProperties.HeadingLevel="Level1" is set on the onboarding title. This is above-average diligence for a small WPF app.
  • That diligence is inconsistent: dynamically-appearing warning text (KelvinSafetyWarning, the "Why these colors?" evidence expanders) has no live-region equivalent, so a screen reader user is not told when a safety warning appears or disappears.
  • Most informational and safety-relevant text in Settings is hard-coded to FontSize="10" (roughly 7.5pt) in Gray/DimGray — small and low-contrast, for a tool whose users may be specifically light/text sensitive.
  • Dark theme (ThemeDetector.ApplyDarkThemeIfNeeded) is applied once at window construction only; if Windows' theme changes while Settings or Onboarding is already open, the open window will not update. The code's own comments note that WPF's default control chrome (focus glow, drop shadows) still assumes a light theme underneath the override — an acknowledged partial fix, not a full theme.
  • Windows High Contrast mode is correctly and deliberately left untouched (a good, considered decision — High Contrast ships its own system palette for a different population). One knock-on effect: the app's own semantic warning color (#FFB03030) has no separately verified High Contrast presentation, since the app doesn't touch colors in that mode at all.

Recommendations

  • Raise all currently-10pt gray informational/safety text to at least 11–12pt with higher-contrast foreground colors, consistent with the app's own more careful dark-theme brush choices elsewhere.
  • Set AutomationProperties.LiveSetting="Assertive" (or equivalent) on KelvinSafetyWarning and similarly on any other text that appears/disappears in response to user input, so assistive technology announces it.
  • Add a SystemEvents.UserPreferenceChanged handler to re-run ApplyDarkThemeIfNeeded on already-open windows, or explicitly document the current limitation in the Settings window itself.
  • No action needed on High Contrast handling itself — it's correct as built. Worth a one-line manual check that KelvinSafetyWarning's text remains legible under a couple of the built-in Windows High Contrast themes, since visibility there depends entirely on the system palette, not this app's styling.

2.5 Motion / Visual Comfort

Found issues (strengths worth preserving)

  • Migraine Mode activation is a single instantaneous step change — deliberately, per the code's own documentation, because a fade would delay relief for someone mid-aura, and because a fade risks looking like a "pulse" if implemented carelessly.
  • Deactivation always fades over 20 seconds at 5 updates/second (FadeDuration/FadeTickInterval in MigraineModeController.cs) — explicitly chosen and commented as staying well clear of flicker/strobe frequencies relevant to photosensitive epilepsy, which overlaps with migraine-with-aura in some patients. This reasoning is sound and should not be weakened by future feature additions (the code comments flag this risk explicitly — good practice).
  • The normal Day/Night/Deep-Night schedule is driven by continuous solar-elevation interpolation, not stepped jumps.
  • Sound feedback on Migraine Mode toggle defaults off, specifically because of phonophobia overlap with migraine — a considered, non-obvious default.

Found issues (real gaps)

  • The one place rapid, un-throttled visual change can occur is the Settings window's live slider preview (see 2.2) — this is the single exception to an otherwise consistently flicker-safe design.
  • None of the app's transitions currently check the Windows "show animations"/reduced-motion system preference. In practice the fade is fixed-duration regardless, so this is lower risk than most apps, but is worth confirming explicitly rather than leaving implicit.

Recommendations

  • Add the slider-preview throttle described in 2.2.
  • Surface the "we never flash — activation is instant, and we always fade out slowly" reasoning to the end user (currently only in source comments) as a short, reassuring note near the Migraine Mode settings section — this is a genuine trust-building fact for a photosensitivity-aware audience.

2.6 Error Handling & Help

Found issues

  • Validation and warning copy is accurate but developer-voiced: "Windows will silently reject it," "Confirmed directly on this hardware," "below roughly 3300K." Honest and precise, but not calm or patient in tone.
  • Save-time validation failures (Kelvin out of range, invalid hex color, malformed bedtime) surface as blocking MessageBox dialogs — functional, but unstyled system dialogs that interrupt flow, versus the inline KelvinSafetyWarning pattern already used successfully elsewhere in the same window.
  • "Help / About..." is the only help entry point, and it is not troubleshooting-oriented (see 2.1). Several conflict states the app already detects well (fullscreen-blocks-overlay, f.lux gamma-ramp conflict, hotkey already claimed by another app, HDR display present) each only ever appear once, as a balloon, at the moment they're detected — there's nowhere to go back and re-read them.

Recommendations

  • Rewrite validation/warning strings in plain language first, with technical detail available but secondary — e.g. "That color is too warm for this screen to show smoothly. Try a slightly cooler value." with an optional "why" expander carrying the existing technical explanation.
  • Replace the blocking MessageBox validation for hex-color and bedtime fields with the same inline-warning-text pattern already used for KelvinSafetyWarning — consistent, less disruptive, and already proven to work well in this codebase.
  • Add one short, plain-language "Troubleshooting" panel consolidating the conflict cases the app already detects, so a user can find that information again without needing to reproduce the original balloon.

3. User Journey Review

3.1 Onboarding / first-time launch

Current experience: On first launch, a modal window opens with four dense paragraphs covering what the app does, Migraine Mode and its hotkey, a medical disclaimer, and a nudge to set a real location (defaults to London). Two buttons: "Got it, maybe later" or "Open Settings Now." Either closes the window and marks onboarding complete permanently.

Expected experience: A short, reassuring "here's what this does and how to get relief fast" introduction that takes seconds to read, with a clear, low-pressure path to set location later if skipped now.

Gap/Friction: Cognitive load is high for a first touch — four paragraphs of continuous prose, plus unfamiliar terms ("Kelvin," "gamma ramp" appears elsewhere but not here specifically — good — though "photophobia," "circadian," and "f.lux" all appear in this first screen). The dismiss button doesn't communicate that anything is still pending.

Proposed fix: Convert to short sequential steps (see 2.3); rename buttons to state the real choice; keep but visually elevate the safety disclaimer.

3.2 Starting a relief mode (Migraine Mode)

Current experience: Triggered via left-click on the tray icon, the global hotkey (default Ctrl+Alt+Shift+M), or the context menu (Toggle / Full / Mild / Deactivate). Activation is instant — tint and gamma shift apply with no fade, tray icon swaps, and a 4-second balloon reads "Migraine Mode ON." An optional sound plays only if explicitly turned on.

Expected experience: A near-zero-effort way to get relief immediately, with a clear (not just momentary) confirmation that it worked and for how long.

Gap/Friction: The activation path itself is excellent — three redundant, fast triggers, and instant (not delayed) relief is exactly right for someone mid-aura. The gap is entirely in the aftermath: once the 4-second balloon disappears, the only way to check current state is to hover the tray icon or open the menu.

Proposed fix: Keep the activation mechanism exactly as-is (it's a strength, not a risk). Add the persistent status surface from 2.1/2.2 so the "still on" state is checkable without hovering.

3.3 Adjusting intensity/timers

Current experience: In Settings, Day/Night color and brightness, Migraine overlay color/opacity/contrast, and auto-revert timing are all slider-driven with paired numeric entry, live-previewed on the real screen, plus two-click "Try Gentle/Strong" and "Try Cooler/Warmer" presets so a user doesn't have to interpret a raw Kelvin or percentage value.

Expected experience: Confidence about what a given value will feel like before committing, without needing to understand units like Kelvin or opacity percentages.

Gap/Friction: The preset buttons are a strong pattern already in place and genuinely solve the "don't make me guess a number" problem. The friction is the unthrottled real-screen preview during fast dragging (2.2/2.5), and the fact that the safety-relevant "why these colors" evidence is hidden inside a collapsed, tiny expander rather than being visible by default.

Proposed fix: Add slider-preview throttling; promote a one-line summary of the evidence rationale out of the collapsed expander (keep the full detail collapsed, but surface "Backed by 2016 migraine-light research; this is a comfort tool, not a medical treatment" as visible text).

3.4 Pausing/stopping

Current experience: Migraine Mode: any toggle action starts an automatic, always-smooth 20-second fade back to the normal schedule — there is no separate "hard stop." Day/Night schedule: "Pause Schedule" (30 min/1 hour/2 hours/Until tomorrow) suspends adjustments without resetting anything, with a "Resume Schedule" item that enables once paused.

Expected experience: An unambiguous, easy-to-find way to stop any active effect, and clear confirmation that it has actually stopped (or is in the process of stopping).

Gap/Friction: The fade-out itself is a genuine safety strength (no sudden brightening). The friction is discoverability of pause/resume state — nothing persistent shows "schedule is paused until 3:00 PM" beyond the tray tooltip.

Proposed fix: Persistent status surface (as above); a confirmation balloon the moment Pause is selected, matching the existing Migraine Mode toggle balloon pattern.

3.5 Understanding "what's happening" / recovering from confusion

Current experience: State lives in tray icon appearance + tooltip text + transient balloons. Help is the onboarding screen. Known conflict states (fullscreen blocking the overlay, f.lux conflict, hotkey conflict, HDR present, auto-start drift) are each detected well and explained in a balloon at the moment they occur, but not persisted anywhere for later reference. An "Auto-start Diagnostics" dialog exists for one specific troubleshooting case and is genuinely well-written and informative.

Expected experience: At any moment, a user should be able to answer "what is this app doing to my screen right now, and why" in a few seconds, and find a written explanation of a problem they remember seeing once but can't reproduce.

Gap/Friction: No persistent status view; help content is onboarding-voiced rather than troubleshooting-voiced; no consolidated place to re-read a conflict warning after its balloon has disappeared.

Proposed fix: Status surface (above) + a dedicated, plain-language Troubleshooting panel consolidating the conflict cases the app already detects reliably.

4. Accessibility & Compliance Notes

  • Keyboard/focus: Standard WPF tab order (source order) applies throughout; no custom TabIndex overrides were found, which is appropriate given the straightforward, single-column layout of every window. The tray context menu uses & mnemonics throughout (e.g. &Toggle Migraine Mode, &Settings..., E&xit), so it is fully operable via keyboard once focused — a real strength. No focus trap or skip-navigation issues were found in any modal window (Onboarding, Settings, Migraine Rating, Profile Name), all of which are simple enough not to need one.
  • Contrast/color: Primary body text and control chrome rely on WPF/Windows defaults (acceptable). The specific risk is the app's own added helper/warning text, most of which is hard-coded to FontSize="10" in Gray/DimGray — this is the one area actively worth raising to a WCAG-AA-conscious size/contrast, especially since some of this text (the Kelvin safety warning, the privacy note, the medical disclaimer) carries safety- or trust-relevant information, not just cosmetic detail.
  • Screen reader labels: Genuinely above-average for a small WPF app — sliders, checkboxes, per-monitor rows, and rating buttons all carry explicit AutomationProperties.Name, and the onboarding title carries AutomationProperties.HeadingLevel="Level1". The gap is dynamic content: warning text that appears/disappears (KelvinSafetyWarning) has no live-region equivalent, so screen reader users won't be told when it appears.
  • Motion safety: The core safety-relevant transition (Migraine Mode activate/deactivate) is well-designed and explicitly reasoned about in the code with photosensitive epilepsy specifically in mind — instant activation, smooth 20-second fade, no strobe/pulse anywhere. The only motion-safety gap found is the un-throttled live slider preview in Settings (see 2.2/2.5), which is a genuine, fixable exception rather than a systemic problem.
  • Theme handling: Dark theme correctly and deliberately defers to Windows High Contrast mode (does not override it) — a considered accessibility decision. Dark theme itself only applies at window-open time, not live, which is a minor but real limitation worth documenting or fixing.

7. Concrete Examples (Before → After)

7.1 Migraine Mode toggle feedback

Before (today)

  • Trigger: left-click tray icon, hotkey (Ctrl+Alt+Shift+M), or context menu — fast and redundant, already a strength.
  • Feedback: instant screen tint, tray icon swaps to migraine_on.ico, one 4-second balloon reading "Migraine Mode ON."
  • Auto-revert time (if set) is visible only by hovering the tray icon.
  • Turning off shows "Migraine Mode OFF — fading back to normal" for 4 seconds, then no further confirmation during the 20-second fade.

After (proposed)

  • Same trigger mechanism — unchanged, it already works well.
  • Balloon copy simplified: "Migraine relief is on." / "Migraine relief is easing off — back to normal in about 20 seconds."
  • Tray tooltip (already updates today) made more prominent via the new status popover: "Migraine relief: ON · turns off automatically at 3:45 PM" or "Migraine relief: ON · stays on until you turn it off."
  • First-use-only note near the settings for this feature: "We turn this on instantly, and always fade it off slowly — sudden brightness changes can be uncomfortable."

7.2 Color-temperature safety warning

Before (today)

"Night color temp of 3200K is too warm for this hardware's gamma ramp — Windows will silently reject it. Confirmed directly on this hardware: values below roughly 3300K fail outright. Try a higher value (3400K is the safe floor found during testing)."

Delivered as a blocking MessageBox at Save time.

After (proposed)
